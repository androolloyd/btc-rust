# Durable execution extensions

The production node records every canonical connect and disconnect in the same redb transaction as bodies, checked undo, coins, indexes, pool, fee observations, stage receipt and active tip. Failed validation/preparation/commit and equal-work side branches cannot advance the journal. A winning branch records old blocks from tip to fork, then new blocks from fork to tip. Journal records reference actual immutable block/undo data; consumer payloads resolve and check that data rather than carrying invented transactions or height-shaped hashes.

The local versioned journal stores fixed 117-byte sequence/kind/height/hash/parent records with SHA256 checksums. Its 124-byte receipt binds the sequence, current height/hash, validated genesis and first-adoption bootstrap height. Startup checks every record's checksum, sequence continuity and actual body/undo ancestry, the final chain binding and every stored consumer cursor. Missing/corrupt/rebound records fail; there is no success fallback or automatic replacement of corrupted history.

For a genuine older validated body-history database, first adoption records the actual current canonical prefix in one transaction. `bootstrap_height` identifies this reconstructed prefix. Past orphan delivery, wall-clock event timing and prior external side effects are unavailable and are not reconstructed. Ordinary node startup never uses the controlled `exex_fixture` acceptance tool; its schema edits run only against stopped temporary stores.

`btc_exex::durable::DurableManager::register` accepts a real `DurableExtension`, with at most eight unique bounded names. It starts and supervises a worker. The worker replays from the durable cursor and treats watch notifications only as wakeup hints, so coalescing or missing live broadcasts does not lose journal entries. The extension validates its newly returned state before actual state and the acknowledged cursor publish in one database transaction. Every worker checks persisted application state even when there are no pending events; an idle cursor cannot bypass state validation. Callback computation holds neither a chain lock nor a database writer; a conflicting same-name update fails rather than overwriting newer state. Application callbacks must be deterministic and keep effects in their returned state: computation can repeat after failure, but a successful state/cursor transaction is not applied twice.

Worker panic/error retries the same unacknowledged event with backoff. Three consecutive failures publish a failed status and cause the configured node supervisor to stop with an error. Successful progress clears the retry state. Shutdown signals and joins workers; restart resumes the last committed cursor. These are trusted in-process Rust callbacks; arbitrary callback code cannot be forcibly preempted. Each state blob is bounded to 1 MiB. A general large protocol index needs an appropriate transactional store rather than silently truncating state to this bound. Journal retention currently keeps the entire history; pruning, compaction, public-chain/load qualification and cross-process consumer ownership are unfinished.

The default `validated-metrics-v1` extension uses actual transaction counts and eligible created/spent coin deltas. Same-block creations/spends cancel, and disconnects reverse both counters. Genesis has no indexed coin event. OP_RETURN and scripts larger than 10,000 bytes are excluded from spendable coin totals, even while the underlying older coin store retains physical unspendable rows. This is an actual validated-chain metric, not Ordinals or Runes protocol indexing.

`getexexinfo` reports the durable journal, actual registered worker status, acknowledged height/hash/sequence and metrics. `caught_up` requires the complete cursor to equal the journal receipt. `getexexjournal(after, count)` exposes at most 64 actual sequence/ancestry/count records per call. Full payloads are supplied to the extension API through checked stored bodies and undo. The offline `exex_plugin` example now replays an existing stopped validated node database instead of merely recording a plugin name.

Legacy `ExExManager` subscriptions and ZMQ remain live broadcast APIs; they do not gain durable external-delivery acknowledgements. Name-only legacy registration now errors explicitly. The Ordinals/Runes examples still detect candidates/count observations and do not provide a complete durable protocol index or reorg undo. Their protocol implementation and independent reference acceptance remain required work.

Primary event ordering evidence is [Bitcoin Core v29 validation](https://github.com/bitcoin/bitcoin/blob/v29.0/src/validation.cpp): successful `DisconnectTip` emits the disconnected block after coin-state flushing, and `ActivateBestChain` emits the connected trace after successful state changes. This project-specific journal adds durable replay and application state transactions; it does not change Bitcoin consensus or define a Bitcoin wire protocol. Actual local and independent Core acceptance results are recorded in BUILD_PLAN.md after verification.
