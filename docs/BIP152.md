# BIP152 compact blocks

The compiled node negotiates witness-inclusive BIP152 version 2 after the
version/verack exchange with witness-capable peers. It uses low-bandwidth
`sendcmpct(announce=false, version=2)` and requests compact bodies for individual
announced blocks. Bulk initial sync continues requesting full witness blocks.
This applies to both inbound and outbound v1/BIP324 connections. The connection
retains Core's offer while initial download consumes other peer messages.

## Wire data and reconstruction

`ShortIdKey` hashes the serialized 80-byte header and little-endian nonce with
**single SHA256**, then uses the first two little-endian u64 values as SipHash
keys. Version 1 uses txids; version 2 uses wtxids. Short IDs contain six
little-endian bytes. The old double-SHA256/block-hash key derivation is removed.

The library has explicit version 1/version 2 primitive operations. Live peer
sessions offer only version 2; the common payload codec uses its witness format.
Version 1 is not advertised as live relay support. Unknown offer versions do
not enable compact requests. Unnegotiated compact requests are declined.

`cmpctblock`, `getblocktxn` and `blocktxn` use canonical CompactSize encodings.
Indices are absolute u16 values in memory and differential values only on the
wire. Counts and minimum remaining bytes are checked before vector allocation;
index addition is checked, full consumption is required, and duplicate,
out-of-order or out-of-range prefilled indices fail. The local bounds are
65,535 transactions and 4,000,000 payload bytes, with transaction weight checked
while decoding. `sendcmpct` requires exactly nine bytes and a boolean 0 or 1.

Partial reconstruction computes IDs from actual supplied transactions. It
never trusts a caller-provided txid map key. Distinct local transactions with
the same short ID leave that position missing; duplicate IDs within the compact
message cause full-block fallback. Completion consumes the snapshot, requires
the exact response hash/count/order and matching short IDs, and checks real
txid merkle linkage, duplicate txids, coinbase positions and weight.

These are structural reconstruction checks. Every completed body enters the
same requested-body queue and validated chain backend as a full block. Script,
UTXO, witness-commitment, contextual/fork and durable atomic commit rules remain
in that backend; reconstruction itself cannot publish coins, pool or tip.

## Runtime bounds and fallback

Peer sessions limit requests to the existing sixteen-block window and account
for both partial storage and queued full bodies under the existing 16 MB
buffer budget. Initial compact responses and missing-transaction responses
have thirty-second deadlines. Known collisions, mismatched completion,
resource limits, missing compact data or deadline expiry request a full witness
block instead. Unsolicited compact bodies/responses are ignored.

Serving uses committed backend blocks and a fresh random nonce. Recent blocks
within five tip heights are eligible for compact responses; older requested
blocks fall back to full witness bodies. `getblocktxn` serves only a bounded
set of previously supplied compact blocks and verifies indices against the
actual stored body. Responses beyond ten tip heights fall back to a full block.
Unavailable committed header metadata returns an error rather than an invented
height. High-bandwidth unsolicited compact announcements are not enabled.

## Independent acceptance

`scripts/core29_compact_blocks.py` generates exact wire/key/reconstruction
fixtures from unchanged checksum-pinned Core v29 helpers. Thirty-two cases
cover both versions, four nonce boundaries, sparse/multiple/absent prefills,
all three message formats and missing-index completion. Five additional
requests cover empty lists, CompactSize width changes, 256 adjacent indices
and the u16 boundary. These synthetic transactions establish wire arithmetic,
not signature or chain validity. Candidate-collision classification has a
private test-only lookup injection; production always uses the actual SipHash.

`scripts/core29_compact_runtime.py`, invoked by the existing Core P2P suite,
uses real mature wallet coins, independently signed spends, regtest PoW and
released Core's chain validator. Each inbound/outbound v1/v2 scenario verifies
actual missing-transaction and shared-mempool compact rounds by block hash,
exact stored bytes and runtime logs. Normal outgoing compact serving is also
required in every scenario.

An explicit hostile v1 peer tests duplicate IDs, wrong response cardinality,
the actual thirty-second missing-response timer, full-body recovery and an
altered-witness compact block. Failed reconstruction/validation leaves the
tip, pool and funded coins unchanged. Correct recovery commits the original
Core-validated block. The client also reconstructs a Rust-mined signed-spend
block from actual `cmpctblock`/`blocktxn` responses with unchanged Core helpers;
Core then independently validates and commits those exact bytes.

The final local gate passes 3,368 tests across 43 suites, formatting, Clippy,
minimal/isolated feature checks and release build (two preexisting ignored
tests). Compact primitive sanitizer acceptance completed 2,819,002 executions
in 31 seconds from 96 independent temporary seeds. The actual framed P2P target
completed 1,117,034 executions in 31 seconds from 48 independent temporary seeds. The isolated `compact-blocks` feature is
checked without Erlay or BIP324 dependencies. The broader consensus/replay and
long adversarial-session gates remain in BUILD_PLAN.md; this is bounded regtest
interoperability, not full public-chain qualification.
